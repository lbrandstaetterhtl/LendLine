# Fix report – Security audit 1

As of 2026-09-24. Basis: `security-audit-1.md`. Checked with `npm run check` in the backend (typecheck, oxlint including type-aware rules, oxfmt, knip: all green) and a smoke test of the API without a database (headers, JSON errors, rate limit, origin check, password length, secret check). Database-dependent paths (LDAP takeover, transactions, token rotation) could not be tested at runtime because this environment had no PostgreSQL/Docker. They were checked by typecheck and code review.

| 1   | No brute-force protection / rate limit (High)         | Fixed           | `backend/src/lib/rateLimit.ts` (new), `backend/src/routes/auth.ts`                  | In-memory limiter with a fixed window. Login: 10 attempts / 15 min per IP + account, 50 / 15 min per IP. Successful logins are refunded so offices behind a NAT do not lock themselves out. Registration: 10 / h per IP. Exceeding it → 429 `RATE_LIMITED`. Every attempt is counted up front, so parallel requests do not help.                                                                                                                                                                                      |
| 2   | Account takeover on LDAP sign-in (High)               | Partially Fixed | `backend/src/services/authService.ts`                                               | When a local account is taken over or its DN changes, all refresh tokens of the account are revoked. This fixes the pre-account takeover (the attacker's session surviving the takeover). **Open:** a second directory entry with the same `mail` still takes over the account's data and role. Locking on a DN change would have locked out legitimate OU moves; a clean solution needs a stable key (`objectGUID`/`entryUUID`) and a migration. As only directory admins can set `mail`, the remaining risk is Low. |
| 3   | Vulnerable dependency `nodemailer` (Medium)           | Fixed           | `backend/package.json`, `backend/package-lock.json`, `backend/src/emails/mailer.ts` | Update to `nodemailer@^10.0.10`. | 4   | Authorization from JWT claims only (Medium)           | Partially Fixed | `backend/src/middleware/auth.ts`                                                    | `requireAuth` loads the user on every request and uses the **current** role. A complete solution needs a session counter (`tokenVersion`) on the user and therefore a migration.                                                                                                                                           |

**Addendum (after audit 2):** Finding 1 of `security-audit-2.md` (Medium, protection only with `NODE_ENV=production`) is fixed for the secret: the placeholder `change-me…` is now refused in every environment; only a short secret still just causes a warning in development (`backend/src/config.ts`, `backend/.env.example`, `README.md`). The seed protection still depends on `NODE_ENV=production` (remaining risk Low, documented in `doc/LendLine.md` §15).

**Operating notes after the update**

- Run `npm install` in the backend (nodemailer 10).
- Installations with the placeholder secret no longer start (in development too), production installations also not with a short secret. Set `JWT_ACCESS_SECRET` to a random value of at least 32 characters first. This invalidates all access tokens; users are signed in again automatically through the refresh token.
- `docker-compose.yml`: whoever used the database from another machine must open it again deliberately.
- Rate limits count per API process in memory and assume that `req.ip` is the real client address (a proxy on loopback that appends `X-Forwarded-For` – like Vite and usual reverse proxy setups).
